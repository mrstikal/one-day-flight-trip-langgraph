## 4. Binding Decisions (do not re-decide)

- Proposal and reservation are separate. `selection_proposals` owns proposed state; a reservation row exists only after an explicit confirmed decision. No "booked" label before confirmation.
- Reservation states are exactly `confirmed`, `superseded`, `cancelled`; `proposed` lives only on proposals. There is no standalone cancel endpoint or cancel UI; `cancelled` is reached only by an approved route-change impact.
- Demo reference: `DEMO-HTL-`/`DEMO-RST-` plus 20 UPPERCASE hex characters (80 random bits), SQL unique, generated by the booking service only. On a reference-specific unique violation, roll back to a savepoint and regenerate; at most 3 attempts; other unique violations are not collisions.
- Replacement: `UPDATE old SET status='superseded'` BEFORE the new `INSERT ... 'confirmed'`; partial unique indexes are checked immediately. Any failure rolls back both; the old reservation stays active.
- Confirmation is a decision response (`confirm_booking`, `acceptedDemoDisclaimer: true`) validated against the trusted resume envelope; model text saying "confirmed" is inert. The public resume schema excludes `modify` and foreign operation IDs.
- Service levels: `effectiveServiceLevel = serviceOverrides[service] ?? defaultServiceLevel`. The hotel control writes the hotel override, never the global default; clearing removes the property (`level: null`). A global change affects only inherited services; confirmed selections are never silently replaced. Breakfast/lunch/dinner overrides are independent.
- Category eligibility is checked against the proposal's bound search/selection target, not blindly against the current global default (`04` section 5).
- `set_program` cannot overwrite a confirmed meal ID, time, or duration; a differing meal ID is staged as a replacement proposal. `null` dinner is valid only with the deterministic no-slot result; a confirmed dinner is never removed.
- Optional restaurant reservations use the same serialized proposal/confirmation flow; no booking is hidden inside program selection or recommendation refresh.
- `validate_selected_logistics` is deterministic and never edits a reservation to pass a check; confirmed meal IDs/times/durations stay fixed.
- Mutating nodes are idempotent under `withEffect(tx, { operationId, nodeName, effectScope })`; replay returns the stored result. A `202` means queued; success renders only after the persisted outcome or SSE event.

## 7. Functions and Interfaces to Implement

Reuse the Phase 03 names; implement only the missing pieces.

| Contract | Input -> Output | Required failure behavior |
| --- | --- | --- |
| `BookingService.propose({ tripId, service, offerId, operationId })` | Phase03 API with admitted revision/fencing context -> proposal | stale inputs/offer rejected; no partial writes |
| `BookingService.confirm({ tripId, proposalId, decisionId, operationId, acceptedDemoDisclaimer, confirmationKey })` | trusted envelope -> reservation result (reference, terms snapshot) | effect replay returns stored result; failures per `09` section 6 table |
| `BookingService.replaceConfirmed(...)` | approved replacement -> superseded old + confirmed new | old superseded BEFORE insert; full rollback on failure |
| `generateDemoReference(serviceKey)` | service key -> `DEMO-*` reference | savepoint-bounded, at most 3 collision attempts; exhaustion -> `REF_GENERATION_FAILED` |
| `stage_selection(ctx)` / `commit_booking(ctx)` / `validate_selected_logistics(ctx)` | graph node contracts per `03` section 4 | deterministic; no LLM; no reservation edits on validation conflict |
| `applySetProgram(ctx, command)` | meal selections + activity IDs -> updated selections / replacement proposal | never moves, removes, or re-keys a confirmed reservation |

## 12. Common Mistakes / Traps

- Creating a reservation when the user only selected a card, or labeling a proposal "booked".
- Superseding after insert (or in a second transaction), tripping the immediate partial unique index.
- Regenerating a demo reference on replay instead of returning the stored effect result.
- Letting the hotel control write `defaultServiceLevel` instead of the hotel override.
- Treating `set_program` as permission to move or remove a confirmed meal.
- Rendering success on `202` or inventing a reference client-side.
- Adding a cancel action that mutates a confirmed reservation without route-change approval.
